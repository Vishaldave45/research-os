# ResearchOS v0.1 Codebase Audit & Gap Analysis

**Date:** 2026-08-21  
**Audit Scope:** Full repository (Frontend, Backend, Database, Schemas, State Management, Security, UX, Persistence)  
**Target Milestone:** ResearchOS v0.1 — Traceability Core Foundation

---

## 1. Executive Summary & System Overview

ResearchOS is designed as a **Connective Traceability Layer** for AI/ML and scientific research teams. Its core purpose is to preserve the end-to-end reasoning chain:

$$\text{Literature/Evidence} \rightarrow \text{Question} \rightarrow \text{Gap} \rightarrow \text{Hypothesis} \rightarrow \text{Experiment} \rightarrow \text{Result} \rightarrow \text{Decision} \rightarrow \text{Claim}$$

The existing codebase contains a rich interactive React/XYFlow frontend and a comprehensive FastAPI async backend architecture. However, in the current state:
1. **Frontend-Backend Disconnect**: The frontend currently operates primarily out of an in-memory Zustand store seeded with static files (`src/data/canonicalWceData.ts`), meaning changes made in the UI do not persist across server reboots, container restarts, or separate browser sessions.
2. **Missing Real API Wiring**: UI components perform in-memory mutations instead of invoking `/api/v1/*` endpoints.
3. **Traceability Querying**: While graph services exist on the backend and visual layouts exist on the frontend, a dedicated backward-trace API route (`GET /api/v1/decisions/{id}/trace`) and its direct frontend visualization hook require unified binding.

## 3. Detailed Audit Findings

### 3.1 Hardcoded & Mock Data
- **Location**: `src/data/canonicalWceData.ts`, `src/store/useResearchStore.ts`
- **Finding**: Initial entities (`INITIAL_QUESTIONS`, `INITIAL_PAPERS`, `INITIAL_GAPS`, `INITIAL_HYPOTHESES`, `INITIAL_EXPERIMENTS`, `INITIAL_RESULTS`, `INITIAL_DECISIONS`, `INITIAL_CLAIMS`, `INITIAL_RELATIONSHIPS`) are hardcoded into frontend constants.
- **Remediation**:
  - Migrate canonical data to the backend database seed runner (`/api/v1/seed`).
  - Frontend store must initialize empty and populate via `GET /api/v1/graph` or individual entity query hooks on workspace mount.

### 3.2 Authentication & Authorization Gaps
- **Finding**: Frontend does not present a login/registration screen; requests do not carry active Bearer JWT tokens.
- **Remediation**:
  - Build `features/auth` with Login/Register forms.
  - Implement token storage (secure session storage/memory with refresh token rotation).
  - Setup Axios/Fetch HTTP interceptors to attach `Authorization: Bearer <token>` and `X-Workspace-Id: <id>`.

### 3.3 Persistence & Database State
- **Finding**: Node modifications, newly added hypotheses, and user-drawn relationship edges are lost when the page reloads or restarts.
- **Remediation**:
  - Every UI action (`CreateNodeModal`, `CreateRelationshipModal`, inline status edits) must call `POST /api/v1/*` or `DELETE /api/v1/*`.
  - Backend must commit all operations to the database with transactional safety.

### 3.4 Backward Traceability Engine
- **Finding**: Users need to ask *"Why was this decision made?"* and receive a deterministic, server-computed proof tree showing the exact path from Decision $\rightarrow$ Result $\rightarrow$ Experiment $\rightarrow$ Hypothesis $\rightarrow$ Gap $\rightarrow$ Question $\rightarrow$ Literature.
- **Remediation**:
  - Expose `GET /api/v1/decisions/{decision_id}/trace` returning the full structured causal chain.
  - Render a dedicated "Trace Evidence" panel in the Node Inspector and Evidence Narrative views.

### 3.5 Reusable Form & Table Infrastructure
- **Finding**: Forms in `CreateNodeModal` and tables in `EntityTableView` contain inline logic without shared abstraction.
- **Remediation**:
  - Build reusable form components with loading states, server-side validation error mapping, and optimistic updates.
  - Standardize table columns, sorting, filtering, and empty/error states across all research entity types.
